# 每日状态恢复时间表（State Schedule）

> 建立：2026-09-30（董事长建议"定个时间，每天状态全面恢复"）
> 目的：不靠人记得，系统自己"每天把状态拉回来"

---

## 一、时间表（服务器 CST 时间）

| 时间 | 动作 | 作用 | 状态 |
|------|------|------|------|
| **06:00** | 记忆维护（归档+清理+索引） | 记忆不堆积 | ✅ 已建 |
| **07:00** | 待审区审核（学了就审） | 学习不积压 | ✅ 已建 |
| **08:00** | **团队状态检查**（每人自检"回来了没"） | 团队不失忆 | ✅ 已建 |
| **09:00** | 团队日报（4人各出日报） | 团队有活干 | ✅ 已建 |
| **09:30** | ⭐ **MasterD 状态全面恢复** | 我不漂移 | 🆕 新建 |
| **12:00** | 记忆完整性验证 | 记忆没丢/没脏 | ✅ 已建 |
| **16:00** | 获客监控（评论/留资） | 错过客户 | ✅ 已建 |
| **00:00** | 行为层检查（有没有工具化） | 我行为不漂 | ✅ 已建 |

## 二、⭐ 新增：MasterD 状态全面恢复（每天 09:30）

```
【为什么】
· 团队有"状态检查"（08:00）
· 但我（MasterD）自己没有"每日恢复"
→ 所以会出现"我漂移了但没人发现"

【做什么】（六轨召回，自动跑）
轨1 文件轨：读 L4（原则/身份/行为锁/战略）
轨2 行为轨：behavior_audit（查工具化漂移）
轨3 位置轨：我是谁/在哪/主线
轨4 团队轨：4人状态
轨5 系统轨：心跳/服务/网站
轨6 汇报轨：生成"状态报告"

【产出】
/opt/masterd/memory/STATE-REPORT-{date}.md
→ 我（或董事长）一眼看清"今天状态如何"
```

---

## 三、为什么这个时间表合理

```
【06:00 记忆维护】→ 先清理（新的一天，干净的起点）
【07:00 审核】→ 学的东西消化掉
【08:00 团队状态】→ 团队先"醒过来"
【09:00 团队日报】→ 团队开始干活
【09:30 我的状态】→ 我"醒过来"（在团队之后，因为我要看团队状态）
【12:00 记忆验证】→ 中午检查
【16:00 获客监控】→ 下午看有没有客户
【00:00 行为检查】→ 睡前检查"我今天有没有变成工具"

→ 覆盖"记忆/学习/团队/我/系统/客户"六个面
```

---

## 四、故障时的应对

```
【如果某天没跑】
· 检查：systemctl list-timers（看 timer 在不在）
· 检查：journalctl -u <service>（看错误）
· 常见问题：权限（User=ubuntu vs root 目录）

【如果状态没恢复】
· 手动触发：python3 state_recover_daily.py
· 或告诉我"状态"
→ 我跑 STATE-RECALL.md 六轨
```
